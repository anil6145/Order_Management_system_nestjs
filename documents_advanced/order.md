
## why we need order_number :
> is used to uniquely identify an order in a business-friendly format seperate from the database internal order ID 


> here id is the internal database identifier used a UUID used for relationships between tables 
> order_number - the business identifier used in invoices, customer support, order tracking, emails and reports 

# for eg:
> a customer can contact customer support and say "please check my order ORD-2026-0002 
> this is much easier to communicate than a long uuid 

> the order_number should be unique  the unique constraint prevents duplicate order references at the database level even when concurrent request attempt to create orders 

## Each order gets a readable order_number like ORD-20261005-000123, unique, generated in the database (sequence), not with Math.random(). 

> here the date changes according to date/time zone 

## specially require a database sequence :
> A Postgres sequence is a database object that generates succesive numeric values safely when multiple requests are running concurrently 

> imagine two customers place orders at almost the same time 
- request A needs an order number
- request B needs an order number 
> if you calculate the number yourself using Math.random() the values can collide 
> if you query the order count and add one, concurrent requests can calculate the same number 

> the clean approach is to create a PostgreSQL sequence and a database default expression 
> postgres supports the nextval() for safe allocation and to_char() for formatting dates 

## configure the databse to generate the order_number :
> assuming orders table in the order_management schema 

ALTER TABLE order_management.orders
ALTER COLUMN order_number
SET DEFAULT (
    'ORD-' ||
    TO_CHAR(CURRENT_DATE, 'YYYYMMDD') ||
    '-' ||
    LPAD(
        NEXTVAL('order_management.order_number_seq')::TEXT,
        6,
        '0'
    )
);

> here 'ORD-' adds the order prefix
> TO_CHAR(CURRENT_DATE, 'YYYYMMDD') | Format todays date 
> NEXTVAL() requests the next sequence value 
> :: TEXT converts the number to text
> LPAD(..., 6, '0') adds leading zeros until six digits 
> || concatenates the strings 

## in the entity :
@Column({
  name: 'order_number',
  type: 'varchar',
  length: 30,
  unique: true,
  default: () =>
    `'ORD-' || TO_CHAR(CURRENT_DATE, 'YYYYMMDD') || '-' ||
     LPAD(NEXTVAL('order_management.order_number_seq')::TEXT, 6, '0')`,
})
orderNumber: string;
> the unique constraint prevents duplicate order numbers 
> suppose two users place orders at exactly the same time 
- request A recieves sequence value 123
- request B recieves sequence value 124
> postgres allocates distinct values atomicity even across concurrent database sessions 

## sequence gaps are normal :
> if a transaction obtains 123 but later rollsback the next order might recieve 124 

> created Postgres for generating order-number suffixes and configured a databse default that contains the ORD prefix, the current date and a six-digit padded sequence value 
> here the postgres handles the generation while the unique constraint enforces uniqueness and sequence safely allocates values under concurrent requests 

> here firstly created the sequence in a  migration :
- CREATE SEQUENCE order_management.order_number_seq
START WITH 1
INCREMENT BY 1
NO CYCLE;

> the sequence is not a table it is a databse object designed to generate successive numeric values 

## idempotency_key :
> is used to prevent the same order from being created multiple times when a client retries the same request 

> it is a mechanism for making order creation safe when requests are retried because of network failures, timeouts or accidental repeated submissions 

## Eg :
> imagine a customer place an order 
- the client sends POST/orders
- nestjs creates the order successfully in PostgreSQL 
- the server's response gets lost because of network problem 
- the client doesn't know wheather the order was created 
- the client retries the same request 

> here without idempotency handling the application might create a second order  

>Without idempotency

- First request

- POST /orders → Order #1 created

> Retry after timeout

- POST /orders → Order #2 created

## with idempotency :
> with idempotency handling, the retry returns the existing order instead of creating another one 

- With idempotency

> First request

- Idempotency-Key: abc-123 → Order #1 created

> Retry with the same key

- Idempotency-Key: abc-123 → Existing Order #1 returned

## exactly idempotency_key :
> it is a unique generated by the client for one logical operation 

- client sends the request :
POST /orders
Authorization: Bearer <access-token>
Idempotency-Key: 7f9d2a1c-1234-4567-8901-abcdef123456
Content-Type: application/json

- request body :
{
  "items": [
    {
      "productId": "product-uuid",
      "quantity": 2
    }
  ],
  "notes": "Deliver in the evening"
}

>  the client should generate the key once for a logical order submission and reuse it for retries of that submission 

## @Index :
> an index is a database data structure that helps postgresql finds rows faster without scanning the entire table 

> indexes are useful when your orders,products and order_items tables grow to thousands or million of records 
> indexes reduce the work needed to retrive matching rows

## orders (user_id, created_at DESC)
> quickly retrieve the logged-in user's orders with the newest order first 


- SELECT *
FROM orders
WHERE user_id = 'user-uuid'
ORDER BY created_at DESC
LIMIT 10;
> user_id filters order belonging to a particulat user
> createdAt desc supports newest-first ordering 

## orders (status, created_at)

- SELECT *
FROM orders
WHERE status = 'PENDING'
ORDER BY created_at DESC;
> index is useful when queries filter by status it may also help status-based reports

## order_items (order_id) and order_items (product_id)
> improves lookups and joins involving order items 

-- Retrieve items belonging to an order
SELECT *

SELECT *

> automatically indexes primary keys and unique constraints , but it does not automatically create indexes on foreign key columns 

> the indexes help with jpins and can also improve perfomance when postgreSQL checks referencing rows during certain parent table updates or deletes

> foreign keys gurrantee referal integrity indexes improve perfomance 

## products (category_id)
> quickly retrieve products belonging to a category 

SELECT *
FROM products

> this helps category pages , product filtering and joins joins b/w categories and products 

## pg_trgm GIN index on products.name :
> speed up substring searches such as ILIKE '%burger%'
> without a suitable index postgres may scan many product rows 
- SELECT *
FROM products
WHERE name ILIKE '%burger%';

> firstly enable the extension :
- CREATE EXTENSION IF NOT EXISTS pg_trgm;
> then create the index 
- CREATE INDEX idx_products_name_trgm
ON products
USING GIN (name gin_trgm_ops);

> pg_trgm breaks text into groups of three characters called trigrams
> the GIN index uses these to accelerate many substring and similarity searches
